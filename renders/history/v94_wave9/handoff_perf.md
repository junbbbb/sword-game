# handoff_perf — props.js 에이전트가 main.js 에이전트에게 (9차 파도, 2026-08-10)

소품 쪽에서 잰 것 중 **main.js 가 만져야 하는 것**만 적는다.
원자료·계측 스크립트는 `renders/history/v94_wave9/perf/` 에 있다.

---

## 0. 먼저: 소품 삼각형은 병목이 아니었다

소품 쪽에서 화면 삼각형을 **47% 줄였는데 프레임타임이 안 변했다.**

| | before | after |
|---|---|---|
| 씬 소품 삼각형(컬링 전, `[props]` 로그값) | 2,417,404 | 1,389,340 |
| 한 프레임에 실제로 그린 삼각형(그림자+화면, 7자리 평균) | 750,128 | 397,117 |
| 소품 화면패스 삼각형 | 244,641 | 57,110 |
| 렌더 1패스 (교대 3라운드) | 9.51 / 9.12 / 6.01 ms | 8.42 / 8.79 / 7.66 ms |

교대 3라운드 짝 비교의 개선율은 +11.5% / +3.7% / −27.6%, **자리별 중앙값 −0.2%** 다.
같은 설정을 두 번 잰 값끼리도 이만큼 벌어진다(= 전부 부하 잡음).
`uptime` load 는 측정 내내 6~35 를 오갔다.

→ **결론: 이 게임은 지오메트리 바운드가 아니다.** 삼각형을 반으로 줄여도 안 빨라진다.
   18~29fps 의 원인은 픽셀이다. 아래는 그 픽셀을 줄이는 자리들이다.

---

## 1. 렌더 스케일 — 실측 곡선

씬 1패스(그림자 패스 포함, 후처리 제외)를 렌더타겟 크기만 바꿔가며 잰 것.
1280x800 을 1.0 으로 둔 배율이다. 한 세션 안에서 순서를 뒤집어 두 번 돌린 평균.

| 렌더 스케일 | 픽셀 | 씬 1패스 |
|---|---|---|
| 1.00 | 1.02 Mpx | 3.41 ms |
| 1.25 | 1.60 Mpx | 4.60 ms |
| **1.50 (지금 값)** | **2.30 Mpx** | **4.94 ms** |
| 2.00 (DPR 상한이 2 였을 때) | 4.10 Mpx | 6.22 ms |

기울기 **0.91 ms / Mpx**. 절편 2.5ms.

**권고: `DPR_CAP = 1.5` 는 그대로 두는 게 맞다.**
이미 들어가 있는 값이고(main.js 31~38행), 2.0 대비 씬패스 1.3ms 를 실제로 번다.
1.25 로 더 내려도 씬패스는 0.34ms 밖에 안 준다 — **더 내릴 이유가 없다.**
`?q=` 오버라이드도 그대로 두면 된다(스크린샷은 `?q=2`, 성능 확인은 `?q=1`).

* 저사양 폴백을 하나 더 둔다면 1.0 보다 **1.25** 를 권한다. 1.0 은 벌이는 0.34ms 인데
  소품이 죄다 각진 바위·절벽이라 가장자리 손해가 클 가능성이 있다(육안 확인은 안 했다).

## 2. ★진짜 큰 자리 — 후처리 체인이 씬보다 훨씬 크다

`renderer.setRenderTarget` 을 가로채 **한 프레임에 어느 타겟에 몇 번 그리는지** 뽑았다
(CSS 1280x800, pixelRatio 1.5 기준. `perf/w9p_rt` 계측):

```
1920x1200@8  x3   ← 씬 타겟(MSAA 8, HalfFloat). EffectComposer 가 핑퐁으로 두 벌 쓴다
2048x2048    x1   ← 그림자맵
1440x900     x4   ← UnrealBloomPass 하이라이트 추출 + 합성
 720x450     x2
 360x225     x2
 180x113     x2
  90x57      x2   ← 블룸 5단 밉 각각 가로/세로 블러
canvas       x2   ← OutputPass
```

한 프레임에 후처리가 훑는 픽셀이 **약 6.05 Mpx**, 씬 타겟은 2.30 Mpx 다.
씬 1패스가 ~5ms 인데 실기 한 프레임이 34ms 라는 것도 이것과 맞는다.

### ★2-1. 블룸이 시작부터 **의도한 크기의 2.25배**로 돌고 있다 (한 줄 고침, 이게 제일 크다)

블룸 밉 0단이 **1440x900** 이다. 그런데 이 화면은 CSS 1280x800 이고,
main.js 의 리사이즈 핸들러(341~348행)는 블룸을 `bloom.setSize(innerWidth, innerHeight)`
= 1280x800 으로 맞춘다. UnrealBloomPass 는 받은 크기의 **절반**부터 시작하니
main.js 가 **의도한 밉 0단은 640x400** 이다. 지금 그 2.25배(면적)로 돌고 있다.

원인: 시작 코드에는 그 줄이 없고, `composer.addPass(bloom)` 이 크기를 스스로 정한다.
`EffectComposer` 는 렌더타겟을 직접 받으면 그 크기를 **CSS 크기로 오해**한다.

```js
this._pixelRatio = renderer.getPixelRatio();     // 1.5
this._width = renderTarget.width;                // 1920 (이미 device px 인데 CSS 로 친다)
addPass(pass) { pass.setSize(this._width * this._pixelRatio, ...); }   // 1920*1.5 = 2880
```
→ 블룸이 2880x1800 을 받고, 밉 0단이 1440x900 이 된다.

**리사이즈를 한 번 하면 저절로 고쳐진다**(핸들러가 다시 크기를 잡으므로).
즉 **시작부터 첫 리사이즈까지 틀린 상태**인데, 평소에 창을 리사이즈할 일이 없으니
게임은 항상 틀린 상태로 돈다. 실측으로 확인했다(`perf/` 의 setRenderTarget 가로채기):

```
리사이즈 전 :  1440x900 x4 · 720x450 x2 · 360x225 x2 · 180x113 x2 · 90x57 x2
resize 후   :   640x400 x4 · 320x200 x2 · 160x100 x2 ·  80x50 x2 · 40x25 x2
```

**고침: `composer.addPass(new OutputPass());` 뒤에 한 줄.**

```js
// ★EffectComposer 는 렌더타겟을 직접 받으면 그 크기를 CSS 로 오해해 패스에 pixelRatio 를
//   한 번 더 곱한다. 리사이즈 핸들러와 같은 크기를 시작할 때도 한 번 먹인다.
bloom.setSize(innerWidth, innerHeight);
```

| | 블룸 밉 | 블룸이 훑는 픽셀 |
|---|---|---|
| 지금 | 1440x900 · 720x450 · 360x225 · 180x113 · 90x57 | **6.05 Mpx** |
| 고친 뒤 | 640x400 · 320x200 · 160x100 · 80x50 · 40x25 | **1.19 Mpx** |

**후처리가 훑는 픽셀 −80%.** 씬 타겟(2.30Mpx)보다 후처리가 2.6배 컸는데 0.5배가 된다.
★값 튜닝이 아니라 **시작 크기 누락**을 메우는 것이다. 임계값 1.02·세기 0.46·반경 0.55 는
그대로 두고, 리사이즈한 뒤의 그림과 똑같아지는 게 맞는 결과다.
★고친 뒤 칼 궤적 발광이 리사이즈 전보다 살짝 부드러워진다(원래 리사이즈하면 그렇게 보였다).
  그 그림이 마음에 안 들면 `bloom.setSize(innerWidth * 1.5, innerHeight * 1.5)` 로
  중간값을 잡으면 된다. 다만 **지금 값(2880)은 어느 쪽도 아닌 사고다.**

### 2-2. MSAA 8 → 4
   `_rt` 가 `samples: 8` 이다. 1920x1200 HalfFloat 8샘플은 타일 메모리를 많이 먹는다.
   조용한 구간에 잡은 짝 비교 한 쌍에서 씬 1패스 **4.73 → 3.61ms (−24%)** 였다
   (그 뒤 라운드는 load 20+ 라 못 쓴다. 수치는 한 쌍짜리니 그대로 믿지 말고
    바꾼 뒤 직접 재 볼 것. 방향은 확실하다).
   4x 와 8x 는 이 톤(툰 셰이딩, 굵은 실루엣)에서 육안 구분이 안 된다.

### 2-3. 핑퐁 타겟이 둘 다 MSAA 8 이다

three 는 `renderTarget2 = renderTarget1.clone()` 이라 samples 까지 복제한다.
씬을 받는 첫 타겟만 멀티샘플이면 되고, 블룸 결과를 받는 두 번째는 그럴 이유가 없다.
`composer.renderTarget2.samples = 0` 한 줄로 멀티샘플 저장·리졸브가 절반이 된다.
(2-2 를 먼저 하면 이건 덤이다. 둘 다 해도 그림은 안 변한다.)

## 3. 그림자맵 2048 → 1024

같은 자리에서 2048 과 1024 를 **연속으로** 잰 18쌍:

| | 값 |
|---|---|
| 중앙값 | 씬 1패스 **−18.6%** |
| 18쌍 중 개선 | 14 |
| 폭 | −32% ~ +36% (부하 잡음) |

**권고: 1024 로 내리는 것을 후보로 올린다. 단 육안 확인이 먼저다.**
그림자 상자가 ±10m 라 2048 이면 텍셀 9.8mm, 1024 면 19.6mm 다.
캐릭터 발밑 접지 그림자가 이 게임 손맛의 일부라(v90 ground) 텍셀이 두 배가 되면
발끝 그림자 가장자리가 뭉갠다. **1536 이 타협점일 수 있다**(텍셀 13mm).
그림자 상자를 ±10 에서 ±8.5 로 좁히면 1024 로도 텍셀 16.6mm 라 손해가 준다
(화면이 앞 10.9m·뒤 3.9m·폭 16.3m 니 ±8.5 로도 화면은 덮는다. `__probe()` 실측값).

## 4. 소품 쪽에서 이미 처리한 것 (main.js 는 안 건드려도 된다)

* 인스턴스 컬링을 **`scene.onBeforeRender` 로 옮겼다.**
  three 는 instanceMatrix 를 `projectObject` 에서 한 번만 올린다. 그 뒤에 부르는
  `mesh.onBeforeRender` 에서 배열을 고치면 **다음 프레임에** 반영된다.
  예전 props.js 가 그 상태였고, 컬링 여유 7m 는 그걸 덮으려던 값이었다.
  → **main.js 가 씬에 `scene.onBeforeRender` 를 새로 물릴 일이 있으면 덮어쓰지 말 것.**
    props.js 는 기존 핸들러를 체이닝해서 문다. 반대 방향도 똑같이 해 주면 된다.
* 화면 패스와 그림자 패스에 **다른 목록**을 준다(한 버퍼에 [화면] + [그림자 전용] 순서로).
  그래서 컬링 여유가 7.0m → 0.6m 로 내려갔고, 화면 소품 삼각형이 245k → 57k 가 됐다.
  그림자는 오히려 정확해졌다(예전엔 카메라 절두체 ±7m 밖의 캐스터를 놓쳤다).
* 소품 콘솔 로그를 `?dev` 게이트로 넣었다. 평시 콘솔은 조용하다.

## 5. 다음 사람이 또 밟을 함정 (계측 쪽)

* **`window.__slow` 로 게임시간을 세우면 카메라가 안 따라온다.**
  `placeCamera(rawDt * 12)` 라 보간계수가 0 이 되고, `__put()` 뒤에도 카메라가 이전 자리에
  남는다. 그 상태로 재면 맵 밖에서 맵을 가로질러 보게 되어 삼각형이 **4배로 뻥튀기**된다
  (이 파도 초반에 한 번 속았다). `__put()` 뒤에 **`window.__probe()` 를 반드시 부를 것**
  (probeCam 이 `placeCamera(0)` 을 지난다).
* **fps·ms 절대값은 못 쓴다.** 같은 설정을 10분 간격으로 두 번 재면 6ms 와 12ms 가 나온다.
  반드시 **같은 세션 안에서 교대**로 재고, 중앙값보다 **최소값**을 볼 것(최소값이 부하 없는
  구간의 실제 비용에 가장 가깝다). `uptime` load 를 같이 적을 것.
* `window.__cap()` 은 `toDataURL` 이 15~29ms 라 프레임 비용 측정에 못 쓴다.
  `renderer.render(scene, camera)` 를 N번 돌리고 앞뒤로 `gl.readPixels(1x1)` 로 동기화해
  나누는 쪽이 잡음이 훨씬 적다(`perf/w9p_bench.mjs` 참고).
* `deviceScaleFactor: 2` 로 컨텍스트를 띄워도 **main.js 의 DPR_CAP 1.5 에 걸려** 1.5 로 돈다.
  해상도별 비교는 컨텍스트를 새로 띄우지 말고 **렌더타겟 크기를 바꿔가며** 재는 게 정확하다
  (`perf/w9p_fill.mjs`).
